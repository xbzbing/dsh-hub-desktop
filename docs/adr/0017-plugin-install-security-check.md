# 0017. 插件安装前静态安全检查

- 状态：已采纳
- 日期：2026-11-08

## 背景

插件由 dsh Host 侧以当前用户权限加载并执行，安装一个来源不明的插件等价于允许第三方代码在本机运行。现有的安装确认区只展示名称、版本、发布时间、下载量和 dsh 兼容性，用户看不到包体是否与 registry 声明一致、是否带安装脚本、是否包含高风险代码特征，也无法区分「新包」与「已被替换的包」。

完整沙箱和运行时行为监控超出桌面端范围；但安装前仍可在不执行插件代码的前提下，读取 registry 元数据并静态解析包体，把已知的高风险信号变成可解释的结论。

## 决策

1. 在 `resolveInstall` 得到精确版本之后、真正执行 `dsh plugin add` 之前执行静态检查。检查对象固定为 `plan.installSpec`，避免检查版本与安装版本漂移。
2. 检查结论收敛为 `pass | warn | blocked | unavailable | disabled`：
   - 任一检查为 `danger` 或 `blocked` → `blocked`，硬阻止，不提供「仍要安装」；
   - 完整性或内容扫描未完成 → `unavailable`，允许确认后安装；
   - 任一检查为 `warn` → `warn`，允许确认后安装；
   - 其余为 `pass`。
3. UI 在安装第二步与升级确认框复用同一面板。`warn` / `unavailable` 才把主按钮改成「仍要安装」，点击即以 `securityAcknowledged` 放行；`blocked` 不渲染安装按钮。主进程在安装/升级入口复用缓存重新判定并执行最终闸门，不能只依赖渲染层。
4. 应用级设置 `pluginSecurityCheck` 默认开启。关闭后主进程直接返回 `disabled`，不发起检查网络请求、不拦截安装；安装框显示静态提示。
5. 检查只做静态读取：不执行包内代码、不运行生命周期脚本、不上传源码。允许访问 npm registry、npm downloads API、GitHub codeload 与 OSV；下载、解包、扫描均有字节数、条目数、单文件大小和总时长上限。
6. 报告在内存中缓存 10 分钟；手动「重新检查」绕过该缓存。缓存 key 包含 spec、安装源和已装插件列表，来源或上下文变化不会命中旧结论。
7. P0 覆盖 npm 深扫、`file:` 本地扫描和基础 GitHub 扫描。GitHub 未固定提交只给 `warn`；构建来源、发布者变更、仿冒名称、非 registry 依赖、原生模块、已知漏洞与恶意软件通告进入结论。仓库事实、传递依赖审计和签名验证留待后续。

## 被否决的备选

- **只做 UI 提示、不做主进程闸门**：渲染层可以绕过，未来新增 CLI 或自动化入口时也会漏掉最终拦截。
- **所有风险都允许覆盖**：完整性哈希不一致、路径穿越、恶意软件通告不是「概率风险」，而是明确的包体/身份异常，覆盖安装没有合理语义。
- **安装前执行包内探测脚本**：会直接触发待检查代码，违背「检查本身不扩大攻击面」的前提。
- **上传 tarball 到云端扫描**：需要新的服务端信任边界和隐私承诺，且社区包源码不适合默认外发。
- **只验 registry 签名**：多数社区包没有签名或 attestation；签名只回答「谁发布」，不回答「包是否安全」。
- **引入沙箱或运行时监控**：工程量和权限模型都超出本功能范围，也不能替代安装前判断。

## 后果

- 用户会在安装前看到来源、完整性、脚本、代码特征、名称与依赖、已知漏洞六类结论；高风险包无法一键安装。
- 静态规则有误报可能：`warn` 保留覆盖入口，`danger` 规则需要保守（远程脚本、凭据外发、混淆执行、挖矿、路径穿越、完整性失败、恶意软件通告）。
- 检查会增加一次安装前的网络与解包开销；通过缓存、并发去重、20 秒总预算和体积上限控制。
- 设置关闭是应用级总开关，不按实例或来源细分；关闭后用户自行承担来源判断责任。
- 通过检查不代表插件安全；面板固定说明「静态检查只能降低风险」。
