# 0021. 本机实例意外退出按退避自动重启

- 状态：已采纳
- 日期：2026-11-27

## 背景

Hub 托管的 dsh 进程会意外退出：模型判断失误后的误操作、上游未捕获异常，或用户被其他终端误杀。
现状是 `local-runtime` 的 exit 处理器只发布 `error`（详情页活动栏显示
「进程意外退出（code=… signal=…）」），实例停在失败态，必须人工再点启动。
`code=0` 的正常退出同样不会自动拉起，表现为「实例自己消失了」。

需要的是**按实例开启的存活策略**：实例意外退出后在后台重新拉起，同时不能让坏配置
（缺依赖、端口始终被占）无限刷进程，也不能在用户明确停止后偷偷复活。

## 决策

1. **配置是实例字段 `autoRestart`，默认 `false`**：与既有 `autoStart` 同层，入口在
   编辑实例对话框；默认关保证不改变用户对「停止」的既有预期。
2. **只覆盖 Hub spawn 的本机实例**：`adopt` 接管的外部进程归用户所有，Hub 不监控也不重启；
   SSH 隧道已有自己的看门狗，HTTP 实例没有本地进程可拉起。
3. **触发条件是「非用户停止」的进程 exit**（包括 `code=0`）。启动超时与健康探测失败
   仍走原失败终态：它们通常指向可复现的配置问题，自动重试只会掩盖原因。
4. **退避与 SSH 隧道同口径**：首次 1s，之后 2s、4s…上限 30s；崩溃前已稳定运行满 60s
   则退避与失败计数重置。**只有「从未就绪」的连续失败计数**，达到 5 次后放弃并提示
   「请手动启动排查」；运行过再崩溃的实例不受次数上限约束，持续按 30s 上限重试。
5. **退出时重读注册表**：运行中关掉开关后，下一次退出不再重启；实例被删除同理。
   手动 `start` 清零退避与计数；`stop`、删除、接管、`stopAll`（应用退出）都会取消
   待执行的定时器并登记取消代，避免停止后迟到拉起。
6. **状态语义不改契约**：退出仍先发布 `error`，`detail` 追加「N 秒后自动重启」；到点后
   沿用 `starting → running`。系统通知仍按原有 `error` 迁移发送，用户能感知崩溃与恢复。
7. 策略决策抽成纯函数 `local-restart-policy.ts`，定时器与配置读取留在 `local-runtime.ts`，
   退避/放弃边界由单测穷举。

## 后果

- 偶发崩溃后实例在数秒内恢复；端口可能漂移，状态事件与注册表回写会同步新端口。
- 崩溃循环时用户仍会收到 `error` 通知（每轮一次），但间隔受 30s 退避约束，不会刷屏。
- 「停止」的语义维持为「用户意图」：手动停止后即使进程随后退出也不会复活。
- 应用退出的清理路径不受影响：`stopAll` 先封死自动重启，再按原有树排空逻辑停止。

## 被否决的备选

- **全局开关（对所有本机实例生效）**：无法表达「这个实例是常驻服务、那个只是临时调试」，
  误开会让临时实例在用户停止后反复复活。
- **默认开启**：会改变既有行为，且旧实例在用户主动杀进程时被重新拉起，属于惊扰。
- **立即无条件重启**：坏配置下变成快速崩溃循环，占满端口与 CPU，也让日志不可读。
- **加上限后彻底放弃所有重启（含运行过再崩溃）**：模型误操作是低频事件，运行过再崩溃
  恰恰最需要「一直活着」；把次数上限限制在「从未就绪」才既安全又满足目标。
- **在 dsh 进程内部加守护**：进程整体退出时内部代码已不在，守护必须由外部宿主承担；
  且 Hub 已是唯一掌握实例生命周期与注册表的一方。
