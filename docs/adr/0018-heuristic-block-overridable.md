# 0018. 启发式检查给出的 blocked 允许确认后安装

- 状态：已采纳，部分取代 [0017](./0017-plugin-install-security-check.md) 的覆盖口径
- 日期：2026-11-09

## 背景

0017 把「任一检查为 `danger`/`blocked`」定为硬阻止，不提供「仍要安装」。实际使用中这条红线挡住过正常插件：`dshmarket@1.73.15` 的 4 条 `content.credential-exfil` 全部来自注释里提到的 `.npmrc`、`undici`、`fetch (`，包内并没有对应的外发代码。遮罩注释的修复解决了这一次误报，但 `content.*`、`scripts.*`、`name.*`、`reputation.*`、`vuln.malware` 都是启发式规则：正则匹配、命名距离、下载量阈值、advisory 版本区间，结构上就不可能没有误报。硬阻止把「规则认为像」当成「确定是」，用户除了换版本或换源没有别的出路。

同一批 `blocked` 里还有另一类结论：哈希与 registry 记录不符、包名/版本与元数据不一致、tarball 含路径穿越条目。这些来自对包体本身的校验，说明取回的不是请求的那个包，用户确认并不能改变这个事实。

## 决策

1. `blocked` 按原因分成两类，放行口径写在 `src/shared/plugin-security.ts`，主进程闸门与渲染层按钮共用同一份判断：
   - 结构性失败：`integrity` 检查为 `blocked`/`danger`（`integrity.mismatch`、`integrity.manifest-mismatch`、`tarball.unsafe-path`、`tarball.manifest-missing`）。仍然硬阻止，不提供安装入口。
   - 启发式结论：内容特征、安装脚本、名称/声誉、恶意软件通告。允许确认后安装，与 `warn`/`unavailable` 走同一条「仍要安装」路径。
2. 启发式 `blocked` 的按钮文案与检查面板徽标、摘要区分于结构性阻止：徽标为「高风险，可确认安装」，摘要说明规则可能误报、风险由用户承担。
3. 主进程仍做最终判定：`securityHardBlocked` 为真时无论 `securityAcknowledged` 为何都抛错；其余结论在未确认时抛「安全检查需要确认」。
4. 0017 的其余决策（检查时机、报告结构、缓存、设置开关、静态读取边界）不变。

## 被否决的备选

- **全部放开，任何 `blocked` 都能确认后安装**：哈希不符、路径穿越、包名/版本与元数据不一致意味着取回的不是请求的那个包，覆盖安装没有合理语义，且用户的确认无法降低这类风险。
- **维持 `danger` 硬阻止**：误报会让正常插件完全无法安装，用户只能换源或关掉整个检查；而关掉检查连真实的 `warn` 也一并不看了，比逐条确认更差。
- **只在渲染层放行**：主进程闸门会继续拒绝，界面显示成功而后端报错；两处判断必须同源。
- **给 `danger` 拆分更细的规则等级**：规则置信度难以静态标定，新增一套分级只会把误报转移到另一个桶里，用户仍需要一个统一的覆盖出口。

## 后果

- 高危规则不再具有「挡住安装」的保证，只保证「必须被看见并显式确认」。证据展示（文件、行号、规则标签）是这条路径的实际防线。
- 结构性失败的硬阻止保持不变，误报只能通过修规则或在设置里关闭检查解决。
- 文案需要同时表达「高风险」与「可以安装」，避免用户以为阻止仍生效。
